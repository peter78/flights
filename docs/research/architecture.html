System Architecture

A layered design that keeps every external dependency — flight data, ground transit, LLMs, fees — behind a swappable interface.

Layers

Clients

PWA-first Next.js web app that doubles as the mobile experience until traction justifies wrapping in React Native / Expo. Streaming results (SSE) so the user sees cheapest-so-far while fan-out continues in the background.

API surface

FastAPI for async fan-out across providers. Two main endpoints:

  • POST /search — takes either a structured SearchRequest or a free-text query; streams Journey results as they arrive.
  • POST /clarify — when NLU returns needs_clarification (ambiguous city, vague date), this endpoint accepts the user's selection and continues.

NLU

One Claude call per user message, with structured tool-use, returning either a SearchRequest or a NeedsClarification. See NLU & LLMs.

Search orchestrator

The hardest layer. Takes a SearchRequest with possibly many origin and arrival candidates, ground-transit windows, and date flex; coordinates parallel calls across providers; composes ground + flight + ground legs into full Journeys; applies a SearchBudget to bound cost and latency.

Cost normalizer + ranker

Joins each itinerary against the fee KB and the user's preferences, produces a CostBreakdown, ranks by a composite score with user-tunable weights.

Provider interfaces

Four protocols. Every external dependency lives behind one of them. PlaceProvider joins the set to support multi-stop trip planning (see Places & POI).

Core data types

SearchRequest:
  origins:          list[GeoPoint | Airport | CityGroup]
  destinations:     list[GeoPoint | Airport | CityGroup]
  depart:           DateRange       # supports flex
  return:           DateRange | None
  passengers:       Passengers
  cabin:            Cabin
  prefs:            PassengerPrefs  # bags, seat selection, max layover, etc.
  ground_modes:     set[Mode]       # {DRIVE, RAIL, BUS, TRANSIT}
  max_ground_time:  Duration        # default 2h
  budget_cap_usd:   int | None
  weights:          RankWeights     # price/duration/stops/etc.

Journey:
  legs:             list[Leg]       # alternating Ground/Flight/Ground
  total_cost:       Money
  total_duration:   Duration
  cost_breakdown:   CostBreakdown
  protected:        bool            # rail-as-flight program
  pricing_confidence: Live | Estimate | Range
  deep_links:       list[BookingLink]

Leg = FlightLeg | GroundLeg

FlightLeg:
  carrier: Airline
  flight_number: str
  from_airport, to_airport: Airport
  depart, arrive: Datetime
  fare_brand: str | None          # populated when provider supports it
  ancillaries_applied: list[Ancillary]

GroundLeg:
  mode: Mode
  from_point, to_point: Place
  depart, arrive: Datetime
  carrier: str | None             # e.g. "DB ICE 1051", "FlixBus N1722"
  price: Money | None
  arrival_uncertainty_minutes: int
  bookable: bool

Provider protocols

class FlightProvider(Protocol):
    capability: ProviderCapability
    async def search(self, req: SearchRequest) -> list[FlightLeg | Itinerary]: ...
    async def get_fare_rules(self, itin) -> FareRules | None: ...

class TransitProvider(Protocol):
    modes: set[Mode]
    regions: set[Region]
    pricing: Live | Estimate | None
    bookable: bool
    async def route(self, origin: GeoPoint, dest: Airport,
                    when: Datetime, passengers: int, bags: int
                   ) -> list[GroundOption]: ...

class LLMProvider(Protocol):
    async def complete(self, messages, tools=None) -> Response: ...
    async def call_tools(self, messages, tools) -> ToolCalls: ...
    supports_cached_prompt: bool
    supports_json_schema: bool

class PlaceProvider(Protocol):
    capability: PlaceCapability    # regions, categories, ratings, hours, ToS-cap TTL
    async def resolve(self, query, *, near=None, category_hint=None) -> list[PlaceCandidate]: ...
    async def details(self, place_id) -> PlaceDetails: ...
    async def search_nearby(self, center, radius_m, category) -> list[PlaceCandidate]: ...
    async def booking_link(self, place_id, when=None, party_size=2) -> str | None: ...

Provider capability flags

Capabilities are introspected at startup so the orchestrator can route work to the right provider without per-provider conditionals downstream.

CapabilityWhy it matters
supports_open_jawOrchestrator falls back to two one-ways if false.
supports_multi_cityThree-or-more-leg trips can be sent as one query.
returns_fare_brandIf true, cost normalizer uses real brand rules; if false, falls back to assumed-cheapest-brand fee profile.
returns_ancillariesIf true, skip fee KB lookup and use provider data.
bookableDrives the deep-link vs. checkout decision.
region setOrchestrator picks providers by geographic coverage.

Request lifecycle

  1. Client sends free-text or structured query to POST /search.
  2. NLU resolves to SearchRequest (or returns needs_clarification).
  3. Orchestrator expands the request into a search plan: candidate airport pairs, date matrix, ground-mode candidates. Applies SearchBudget.
  4. Pruning passes (isochrone, negative cache, historical price floor) drop dominated combinations.
  5. Parallel fan-out across FlightProviders and TransitProviders.
  6. Composition pass assembles full Journeys, enforces connection rules.
  7. Cost normalizer attaches breakdowns; ranker scores.
  8. Top-K stream out via SSE; remaining results trickle in.
  9. Each result is also written to price_observations for the history database.

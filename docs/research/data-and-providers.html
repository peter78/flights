Flight Data & Providers

Start with fast-flights; architect so any GDS, aggregator, or future scraper can drop in without touching the orchestrator.

The decision

Use fast-flights as the v1 flight provider. Wrap every external dependency behind a FlightProvider protocol so providers are swappable per-deployment and per-request.

Why fast-flights is free, already integrated, and supports multi-city queries (open-jaw, multi-leg). Booking APIs (Duffel, Amadeus) give better fare-brand and ancillary data but cost money, require partnerships, and aren't necessary until booking enters scope.

Provider abstraction

class FlightProvider(Protocol):
    name: str
    capability: ProviderCapability

    async def search(
        self,
        req: SearchRequest,
        budget: SearchBudget,
    ) -> AsyncIterator[Itinerary]: ...

    async def get_fare_rules(
        self,
        itinerary: Itinerary,
    ) -> FareRules | None: ...

    async def deep_link(
        self,
        itinerary: Itinerary,
    ) -> str: ...

@dataclass
class ProviderCapability:
    regions: set[Region]
    supports_open_jaw: bool
    supports_multi_city: bool
    returns_fare_brand: bool
    returns_ancillaries: bool
    bookable: bool
    typical_latency_ms: int
    rate_limit_per_minute: int | None

Each adapter is responsible for translating the universal SearchRequest into its own request shape and normalizing results into Itinerary/FlightLeg. The orchestrator never sees a provider-specific type.

The FastFlightsProvider adapter

class FastFlightsProvider:
    name = "fast-flights"
    capability = ProviderCapability(
        regions={Region.GLOBAL},
        supports_open_jaw=True,        # multi-city query type
        supports_multi_city=True,
        returns_fare_brand=False,      # forces estimate-mode cost
        returns_ancillaries=False,
        bookable=False,
        typical_latency_ms=4000,
        rate_limit_per_minute=None,    # Google's, not declared
    )

    async def search(self, req, budget):
        # 1. Translate SearchRequest -> fast_flights.Query
        # 2. Call get_flights() via primp client (or Bright Data integration
        #    when configured)
        # 3. Parse and normalize each result into Itinerary
        # 4. Yield as they're ready

Choosing providers at request time

Multiple providers can run in parallel; the orchestrator dedupes results by (carrier, flight_number, date, price). Capability flags decide eligibility:

  • If SearchRequest.is_open_jaw, drop providers without supports_open_jaw from the candidate set.
  • If user requested bookable_only, drop providers with bookable=False.
  • If SearchRequest.region doesn't intersect capability.regions, skip.

The swap path

Three swaps that should be a configuration change, not a refactor:

  1. fast-flights → Duffel when booking enters scope. The adapter's search() + deep_link() change; downstream code doesn't. Fare-brand-aware cost breakdowns activate automatically because returns_fare_brand flips to true.
  2. fast-flights → Kiwi.com Tequila for users opting into self-transfer / hidden-city options. Run as a parallel provider; results carry a virtual_interlining=True flag.
  3. Bright Data proxy on/off per request. Already integrated in fast_flights; expose as a feature flag for users on flaky regions.

Operational concerns with fast-flights

Watch Three failure modes to plan for from day one.

1. Google rate-limits / blocks

At any meaningful traffic, Google will start rate-limiting from a single IP. Bright Data is already wired in (fast_flights/integrations/bright_data.py). Plan: enable Bright Data by default for production; allow a "direct" mode in dev. Budget: residential proxy traffic is the main marginal cost.

2. UI changes break the parser

The parser pulls fields out of a JS-embedded payload by array index (see fast_flights/parser.py). Index drift = silent breakage. Mitigations:

  • Schema sentinels: assert known-shape invariants (number of fields, type of price) and raise loudly on mismatch.
  • Daily canary search against a fixed query; alert on schema mismatch or zero results.
  • Pinned fast-flights version per deploy; staged upgrades.

3. Fan-out amplifies fragility

Multi-origin search means N parallel Google requests per user search. Each is a chance to fail or get throttled. Mitigations:

  • Per-provider circuit breaker: after K failures in 60s, mark unhealthy for M minutes, return cached + estimated.
  • Per-search retry budget (e.g. 2 retries, then drop that candidate from the result set rather than failing the whole search).
  • Use stale cache + SWR (see Caching) to keep results coming even when providers are flapping.

Reference data

Two static datasets the providers all share:

  • airports.csv (already in enums/) — IATA + ICAO + lat/lon + city + country. Extended with served-by-rail station code, time-zone, and "primary" boolean for the city-group resolver.
  • airlines.json — carrier code, name, alliance, fare-class profile reference. Populated by the airline-fee KB worker (see Cost Transparency).

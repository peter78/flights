Evals & Measurement

Split by layer, not by feature. Four tiers, different cadences, different oracles. The fixture suite catches regressions on every PR; the live suite catches reality drift overnight; production telemetry tells you what users actually experience.

The problem

A flight-search engine has at least five things that can quietly break: the NLU misreads a query, the orchestrator prunes too aggressively, the cost normalizer applies the wrong fare brand, the ranker picks a dominated option, a provider parser silently degrades. Each fails on its own timescale, with its own oracle (what would the right answer have been?), and at its own cost to grade. One eval can't cover all of them.

The reframe: build a measurement system, not a test suite. Each layer gets the eval that fits its bar.

Tier 1 — Fixture-based unit evals

Record provider responses (fast-flights HTML, HAFAS JSON, Claude tool-call outputs, fee-page snapshots) once. Replay forever. Each component graded in isolation against frozen inputs. This is the eval surface that runs on every PR and gates the build.

Why fixtures Live providers move. A test that passed yesterday and fails today because Google Flights repriced isn't a regression — it's noise. Fixtures separate "the code changed" from "the world changed", which is the only useful signal in CI.

Gate condition

  • Per-category accuracy drop > 3% → fail the build.
  • Any new category at < 80% → fail the build (forces eval set to grow with features).
  • Total runtime cap: 30s. Anything slower belongs in Tier 2.

Tier 2 — Live end-to-end evals

A small golden set (~30 queries) hits the running system with live providers. Output compared to an oracle. Runs nightly, posts a report.

Two oracles, both flawed; use both

  • Comparator scrape — for each query, fetch the cheapest result from Google Flights / Skyscanner / Kayak at the same wall-clock minute. Metric: "found cheapest within $X / Y%". Falls apart for multi-airport and intermodal queries because the comparators don't do them, so flag those queries as comparator-exempt.
  • LLM-as-judge — another Claude call grades each top-3 result against a rubric ("is this a reasonable answer to the user's query?"). Stable if you also hand-grade 10–15% of the same set as ground truth and re-validate the judge weekly. Catches the multi-axis cases that comparators can't.

Split metrics by archetype

Average accuracy hides regressions in the long tail. Bucket every golden query into one of:

  • Simple round-trip (single origin, single dest)
  • Multi-origin (catchment-area search)
  • Open-jaw
  • Intermodal (rail/bus + flight)
  • Date-flexible (±N days, cheapest week)
  • Multi-stop trip (POIs → flight legs)

Report accuracy per bucket. A simple-round-trip regression and an intermodal regression are different failures with different owners.

Stability as its own metric

Same query, run twice five minutes apart. How much does top-3 churn? High churn means the ranker is too tightly coupled to noisy provider responses, or that scoring weights are pathologically close on common journeys. Track median Jaccard overlap on top-3 across paired runs; alert under 0.7.

Tier 4 — Price-history backtests

Once price_observations has ~3 months of data (see Caching), the "deal score" and any "wait or book" predictions need their own eval surface.

  • Walk-forward backtest: withhold the most recent 30 days. Train / fit the score on data older than that. Predict on the held-out window. Score: ranked correlation of predicted deal-score vs. actual price percentile.
  • Per-route holdout: top 50 routes, evaluated independently — a model that nails JFK–LHR but fails on intra-EU has a coverage problem hidden by a global average.
  • Counterfactual: for predictions that say "wait", measure outcomes 7 / 14 / 30 days later. False-positive cost (user waited, price rose) is the killer here, not average accuracy.

The hardest part: defining "correct" end-to-end

Cheapness isn't the only axis. Open-jaw, intermodal, time-of-day preferences, transit-budget tolerance all trade off. A "wrong" top-1 might just be a different valid trade. Three practical disciplines:

  1. Pair an objective metric with a subjective one. "Found-the-cheapest rate" alongside "LLM-judge top-3 reasonableness". Both drifting the same direction is signal; divergence means the rubric or the ranker is mis-specified.
  2. Calibrate the judge. The LLM judge is itself a model. Hand-grade 10–15% of the eval set; track judge agreement with human ground truth weekly. If judge accuracy drops, retune the rubric before trusting its verdicts.
  3. Surface uncertainty, don't paper over it. If two providers disagree on a price, or the ranker is split between two near-identical journeys, log both. Don't pick a winner just to make the eval green.
Anti-pattern Don't grade end-to-end correctness by re-running the same model that produced the answer. The judge must be a different prompt, different system message, and ideally a different model family. Otherwise you're grading on a curve.

Sample graders

NLU grader (Tier 1)

from dataclasses import dataclass
from models import SearchRequest, NeedsClarification

@dataclass
class NLUCase:
    query: str
    expected: SearchRequest | NeedsClarification
    archetype: str                 # simple | open_jaw | intermodal | ...
    must_clarify_on: set[str] = ()  # field names that should trigger clarification

def grade_nlu(case: NLUCase, actual) -> dict:
    structural = isinstance(actual, (SearchRequest, NeedsClarification))
    if not structural:
        return {"pass": False, "reason": "invalid output type"}

    # behavior: did it clarify when expected?
    if case.must_clarify_on:
        if not isinstance(actual, NeedsClarification):
            return {"pass": False, "reason": "should have clarified"}
        return {"pass": actual.field in case.must_clarify_on}

    # semantic: field-by-field match on the structured request
    diffs = []
    for field in ("origins", "destinations", "depart", "return_",
                  "passengers", "cabin", "ground_modes"):
        if getattr(actual, field) != getattr(case.expected, field):
            diffs.append(field)
    return {
        "pass": not diffs,
        "diffs": diffs,
        "archetype": case.archetype,
    }

Ranker grader (Tier 1)

from scipy.stats import kendalltau

def grade_ranking(expected_order: list[str], actual_order: list[str]) -> dict:
    # Journey IDs only; assumes both lists contain the same set
    tau, _ = kendalltau(
        [expected_order.index(j) for j in actual_order],
        list(range(len(actual_order))),
    )
    top3_match = set(expected_order[:3]) == set(actual_order[:3])
    return {
        "kendall_tau": tau,
        "top3_set_match": top3_match,
        "pass": tau >= 0.7 and top3_match,
    }

LLM judge (Tier 2)

JUDGE_RUBRIC = """
You are grading a flight-search system's response to a user query.
Rate the top-3 journeys returned, 1–5, on each of:
  - relevance:    does the journey match the user's stated constraints?
  - cheapness:    is the total cost competitive vs. what's available?
  - reasonableness: would a knowledgeable travel agent surface this?
Return strict JSON: {scores: [{relevance, cheapness, reasonableness}, ...],
                    overall: 1-5, notes: str}
"""

async def judge_response(query: str, top3, llm: LLMProvider) -> dict:
    msg = [
      {"role": "system", "content": JUDGE_RUBRIC},
      {"role": "user", "content": format_judge_input(query, top3)},
    ]
    raw = await llm.structured(msg, schema=JUDGE_SCHEMA)
    return raw

Cost grader (Tier 1)

def grade_cost_breakdown(expected: CostBreakdown, actual: CostBreakdown,
                         tolerance_cents: int = 100) -> dict:
    diffs = {}
    for line in ("base_fare", "taxes", "bag_fees", "seat_selection",
                 "ground_transit", "parking"):
        exp = getattr(expected, line, 0)
        act = getattr(actual, line, 0)
        if abs(exp - act) > tolerance_cents:
            diffs[line] = {"expected": exp, "actual": act}
    return {
        "pass": not diffs,
        "diffs": diffs,
        "total_delta_cents": abs(expected.total_usd - actual.total_usd) * 100,
    }

Eval data management

  • Fixtures are checked in. Recorded provider responses live in git so a developer can run Tier 1 offline. Refresh policy: re-record quarterly or whenever a parser changes; keep the old fixture as a regression case.
  • Golden sets are versioned, not edited in place. Each addition gets a PR with rationale. Hand-grader signs off.
  • PII discipline. Real user queries don't enter the eval set without scrubbing names, dates of birth, payment info. Synthesize travel intents; never copy production payloads verbatim.
  • Judge calibration set is sacred. Hand-graded ground truth for ~15 cases that the judge never sees during training / prompt iteration. If you tune the rubric against this set, it's no longer a calibration set — rotate it quarterly.

What to build first

  1. Tier 1 NLU evals first. Highest ROI, smallest blast radius, no provider dependency. Pairs with the NLU work already planned for Phase 1.
  2. Tier 1 cost-normalizer evals second. Deterministic, easy to grade exactly, catches a class of error that's otherwise invisible until users complain.
  3. Tier 3 production telemetry next. Cheap to set up, immediately tells you what's real. Don't wait for product-market fit.
  4. Tier 1 ranker + composition when those components stabilize.
  5. Tier 2 live e2e when there's an orchestrator worth grading end-to-end.
  6. Tier 4 backtests when price_observations has 3+ months of data — not before.
Compounding asset The eval harness is the second-most-valuable artifact this project produces, after the price_observations table. It outlives any single model choice, makes the next LLM swap a config change, and turns "did this PR break anything?" into a question with an answer.

Risks worth tracking

  • Goodhart on golden sets. The team optimizes for what's measured. Rotate fresh queries in monthly; retire ones the system has memorized.
  • Judge drift. Newer Claude versions may grade the same answer differently. Pin the judge model version; re-calibrate when bumping.
  • Comparator legitimacy. Scraping Google Flights / Skyscanner for oracle data sits in the same ToS-grey zone as fast-flights. Keep volumes low; this is internal eval traffic, not user-facing.
  • Eval cost creep. Tier 2 nightly + Tier 4 weekly + LLM-judge calls add up. Budget < $50 / month for v1; revisit at scale.

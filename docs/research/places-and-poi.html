Places & POI Search

Resolving landmarks, restaurants, and attractions from free text — so the agent can plan flights and ground transit around the places the user actually wants to visit.

The problem

Multi-stop trip planning starts with places, not airports. A user says "Louvre, then Versailles, then a Michelin restaurant in Lyon" and expects the agent to figure out the city clusters, the flight legs between them, and the ground transit within them. To do that, the NLU layer needs to resolve each free-text place reference into structured data — name, coordinates, city, category — and, where the use case calls for it, ratings, hours, photos, menus, and bookable links.

No single source covers all of that well. The plan is to compose, behind a swappable interface, the same way FlightProvider composes flight sources.

Discovery / curation

  • Wikivoyage — scraping is fully legal under CC-BY-SA; great for offline seeding.
  • Atlas Obscura, Eater, Michelin Guide — scraping is brittle and ToS-grey; treat as curated seed lists.
  • LLM-generated suggestions (Claude, the existing NLU layer) grounded against a free POI source — cheap and surprisingly effective for "best X in Y" prompts.

The three cost models

Sized at 1k searches/day × 3 POI lookups avg × 70% cache hit ≈ 27k live calls/month.

Model 1 — Free / OSS first (~$0–$50/mo)

  • Self-hosted Nominatim + Overpass + Wikidata for geocoding and category discovery.
  • Foursquare free tier (500/day) + Yelp Fusion free tier (500/day) for the small slice that needs ratings or hours.
  • Affiliate deep-links (OpenTable, Viator, GetYourGuide) for booking — free to integrate, revenue share on the way back.
  • Gaps: no photos at scale, spotty restaurant ratings outside the US, no menus.

Model 2 — Best quality, paid (~$200–$800/mo realistic, ~$2.5k naive)

  • Google Places API primary for metadata + reviews + photos.
  • Yelp Fusion paid tier for US restaurant ranking.
  • TripAdvisor Content API for attractions + hotels + reviews.
  • Mapbox Geocoding for fast structured lookups.
  • Affiliate booking layered on top.
  • Naive cost at 27k live calls/mo of Google Places Text+Details+Photos ≈ $1.5–2.5k/mo before free credit. With 7-day caching and lookup dedup, realistically $200–500/mo.
  • Watch: Google's ToS caps caching at 30 days for most fields and forbids storing reviews verbatim — the cache has to respect that.

Model 3 — Strictly free / OSS-only (~$0/mo, real engineering cost)

  • Nominatim + Overpass + Wikidata + Wikivoyage scraping.
  • LLM-grounded suggestions to compensate ("based on Wikipedia and Wikivoyage, here are 5 Lyon restaurants known for X").
  • Affiliate booking still works.
  • Gaps: no reviews, no photos, no hours confirmation, no menus. Can't reliably rank restaurants.
The pick Hybrid — OSS-first with a paid escalation layer. Same playbook as the flight side: cheapest path tried first, paid only when the cheap path can't answer, all behind one interface.

The PlaceProvider interface

Same pattern as FlightProvider / TransitProvider / LLMProvider. Capability flags let the orchestrator route per-query without provider-specific branching downstream.

class PlaceProvider(Protocol):
    name: str
    capability: PlaceCapability

    async def resolve(
        self,
        query: str,
        *,
        near: GeoPoint | None = None,
        category_hint: PlaceCategory | None = None,
        limit: int = 5,
    ) -> list[PlaceCandidate]: ...

    async def details(
        self,
        place_id: str,
    ) -> PlaceDetails: ...

    async def search_nearby(
        self,
        center: GeoPoint,
        radius_m: int,
        category: PlaceCategory,
        *,
        rank_by: Literal["relevance", "rating", "distance"] = "relevance",
    ) -> list[PlaceCandidate]: ...

    async def booking_link(
        self,
        place_id: str,
        when: Datetime | None = None,
        party_size: int = 2,
    ) -> str | None: ...

@dataclass
class PlaceCapability:
    regions: set[Region]
    categories: set[PlaceCategory]      # LANDMARK, RESTAURANT, ATTRACTION, HOTEL, ...
    returns_ratings: bool
    returns_hours: bool
    returns_photos: bool
    returns_reviews: bool
    has_booking: bool
    cache_ttl_max_days: int             # 7 for Google, 30 for OSM, etc.
    license: License                    # ODbL, GoogleToS, YelpToS, ...
    typical_latency_ms: int
    rate_limit_per_minute: int | None

@dataclass
class PlaceCandidate:
    place_id: str                       # provider-scoped
    name: str
    coords: GeoPoint
    city: str
    country: str
    category: PlaceCategory
    rating: float | None
    price_tier: int | None              # 1–4 ($-$$$$)
    provider: str
    confidence: float

The hybrid recommendation (what I'd actually build)

Three tiers, tried in order:

  1. Tier 1 (free, always first): self-hosted Nominatim + Overpass + Wikidata. Covers ~80% of resolve_poi calls (well-known landmarks, museums, neighborhoods).
  2. Tier 2 (free w/ quota): Foursquare free tier when hours or category needed but reviews aren't.
  3. Tier 3 (paid, only when prior tiers can't answer): Google Places for ambiguous restaurants, photo-rich answers, rating-ranked discovery. Yelp Fusion for US-specific restaurant ranking.
  4. Booking: affiliate deep-link out — OpenTable, Viator, GetYourGuide, Tiqets. No inline booking in v1.

Multi-stop trip composition

How POIs feed back into the existing search engine:

  1. NLU extracts a list of POI references from the user message via a new resolve_poi tool (see NLU & LLMs).
  2. PlaceProvider resolves each reference to a PlaceCandidate, asking the user for disambiguation when confidence is low (same flow as resolve_location today).
  3. POIs are clustered by city / region using the existing city_groups + a small radius rule.
  4. Each cluster becomes a destination in a multi-leg SearchRequest. Order is preserved when the user implies it ("Louvre, then Versailles, then Lyon"); optimized otherwise.
  5. Ground transit within a cluster is computed by the existing TransitProviders (see Ground Transit).
  6. Results are presented as a single multi-stop journey with bookable deep-links per stop.
"Louvre, then Versailles, then a Michelin restaurant in Lyon"
        ↓ NLU resolve_poi × 3
[Louvre (Paris), Versailles (Paris)], [Michelin (Lyon, ambiguous → clarify)]
        ↓ cluster
PAR (Paris) → LYS (Lyon)
        ↓ SearchRequest with two destinations, ordered
flights + ground + ground = multi-stop journey

Caching strategy

POI data is much less volatile than flight prices — addresses move rarely, ratings move slowly, hours change seasonally. But provider ToS constrains how long you can hold data; design the cache around it.

place_cache (
    cache_key       text primary key,       -- hash(provider, query, near)
    provider        text not null,
    place_id        text,                   -- provider-scoped
    payload         jsonb not null,         -- normalized PlaceCandidate(s)
    fetched_at      timestamptz not null,
    expires_at      timestamptz not null,
    license         text not null           -- enforced on read
);
create index on place_cache (expires_at);
create index on place_cache (provider, place_id);

-- TTLs by provider (enforced at write):
--   Google Places       :  7 days   (under 30-day ToS cap)
--   Yelp Fusion         :  7 days
--   Foursquare          : 14 days
--   OSM / Wikidata      : 30 days
--   Nominatim self-host : 30 days

Same negative-cache idea from Caching applies: cache "no Michelin restaurant matching X in Lyon" for 7 days, soft-invalidate on user-reported staleness.

Integration with existing layers

  • Architecture — PlaceProvider is the fourth provider protocol alongside FlightProvider, TransitProvider, LLMProvider.
  • NLU — new resolve_poi tool with disambiguation flow; the user's place references become structured POIs before flights are searched.
  • Caching — new place_cache table with provider-aware TTLs.
  • Cost — place-search calls show up in the cost breakdown as a small fixed overhead per search (~<$0.01/search at Tier-1, <$0.05 when Tier-3 fires).
  • Ground Transit — ground transit within a city cluster connects resolved POIs; existing connection rules apply.

Risks worth tracking

  • Google Places ToS — 30-day cache cap on most fields, no verbatim review storage, attribution required. The cache schema has to enforce per-provider TTLs at write time.
  • Yelp Fusion ToS — caching restrictions plus attribution; some UI patterns prohibit mixing Yelp data with non-Yelp data.
  • OSM ODbL — share-alike applies to derivative databases. Using OSM in your product is fine; redistributing a derived DB is the concern. Attribution required.
  • Affiliate compliance — registered-partner requirement, link disclosure, commission structures vary by program.
  • POI volatility — restaurants close, hours shift seasonally. Same negative-cache and user-feedback patterns as on the flight side.
  • Disambiguation cost — "a Michelin restaurant in Lyon" forces a clarification round-trip. Mitigate by letting the agent offer 3 top picks inline rather than asking open-endedly.

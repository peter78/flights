Caching & Indexing

Full pre-indexing of prices doesn't work. Layered caching plus a price-history database does — and the price history compounds into a moat.

Why "index everything" fails for prices

  • Combinatorial: ~500 popular airports × 500 = 250k pairs × 365 days × 4 cabins ≈ 180M queries per refresh cycle. At ~1 req/s through a scraper, that's years.
  • Volatility: airline revenue-management systems reprice every few minutes. A 1-hour-old cached price is often wrong; a 24-hour-old one is misleading enough to break user trust the first time they click through.
  • Inventory: even when a price holds, the seat may be gone. You'd be advertising offers that don't exist.
  • Long tail: 80% of searches hit common routes, but the other 20% are exactly the ones the user actually needs answered.
Reframe The question isn't "cache or not". It's what's stable enough to cache, and what cache pattern fits each thing.

1. Query-result cache

Table stakes. Redis, keyed by a normalized hash of SearchRequest.

key = sha256(
    canonical_json(SearchRequest.normalize())  # drop None, sort sets
)
ttl_browse   = 10 * 60     # 10 min for general browsing
ttl_select   =  1 * 60     # 1 min once user has selected (or skip cache)

Stale-while-revalidate: on a hit older than 50% of TTL, return the cached value and kick off a background refresh. Push updated results via SSE when they arrive. Net effect: repeat-query latency drops from ~5s to ~50ms; provider load drops 70–90% on popular routes.

2. Price-history database (the moat)

Every search result that returns to a user is also written, append-only, to price_observations. Grows passively with traffic; no extra scraping budget required.

price_observations (
    id              bigserial primary key,
    observed_at     timestamptz not null,
    origin          char(3) not null,        -- IATA
    destination     char(3) not null,
    depart_date     date not null,
    return_date     date,
    cabin           cabin_enum not null,
    carrier         char(2),                 -- marketing carrier
    stops           smallint,
    price_usd       numeric(10,2) not null,
    fare_brand      text,                    -- null when provider doesn't supply
    provider        text not null,
    journey_hash    bytea                    -- dedupe within a session
);
create index on price_observations (origin, destination, depart_date);
create index on price_observations (observed_at);

What it unlocks

  • Deal score: "$412 LAX→NRT for late June is in the cheapest 18% historically." Hopper-style, but computed from your own data.
  • Cheapest-week widgets without re-querying live for a date matrix.
  • Price-drop alerts — subscribe a user to a (route, date-window) and notify when current prices fall below the historical median.
  • "Wait or book" predictions once you have ~6 months of data on a route.
  • Pruning input: the orchestrator uses historical floors to skip provider calls for candidate pairs that can't beat the current best total.
Cold start Seed by running a nightly scrape of the top 200 routes for ~90 days, then let organic traffic take over. ~2–3 months in, the model becomes meaningful.

3. Negative cache

"No flights JFK→LCY direct" is a common, slow-to-prove result. Cache the absence too.

negative_cache (
    request_hash    bytea primary key,
    expires_at      timestamptz not null
)
default ttl = 6 hours for "no service today"
default ttl = 30 days   for "carrier doesn't serve this pair"

Big win for intermodal fan-out: many candidate (city → airport → destination) tuples have no service at all, and skipping them with one DB lookup keeps the search budget intact.

4. Route index

"Does carrier X serve route Y at all, currently?" Powers fan-out pruning.

route_index (
    origin       char(3) not null,
    destination  char(3) not null,
    carrier      char(2) not null,
    nonstop      bool not null,
    days_of_week smallint,           -- bitmask
    season_start date, season_end date,
    last_seen_at timestamptz not null,
    primary key (origin, destination, carrier)
)

Refreshed monthly from a combination of: results observed in price_observations (organic), Wikipedia airline route maps (curated), and carrier site indexes (best-effort).

5. Schedule index

Nightly job records which flights exist for the top N routes (no prices, no fan-out). Lets the UI render skeleton results instantly while live prices fetch:

┌─ Delta DL47, nonstop, departs 11:35 − − − checking price…
│
│ United UA1872, 1 stop ATL, departs 14:10 — $612 (live)
└

6. Isochrone cache (ground transit)

Pre-computed "ground area reachable from each airport within T hours" stored as PostGIS polygons. Refreshed quarterly. See Ground Transit for the details.

What about scraping airline sites directly?

Don't (yet) Direct airline scraping is tempting but the wrong v1 trade.
  • Anti-bot is industrial: most major airlines run Akamai Bot Manager, PerimeterX, or DataDome. Headless browser + residential proxies might work and breaks weekly.
  • Maintenance burden: each airline is a bespoke scraper. ~20 carriers = 20 things that break independently.
  • Legal exposure: Ryanair in particular has sued scrapers in EU courts and won some judgments. US case law (hiQ v LinkedIn) is friendlier but the postures are aggressive.
  • What you'd gain over fast-flights is fare brand and accurate ancillaries — both available through Duffel (~free at low volumes) when the time comes.

The fee-page LLM extractor (see Cost) gets you ancillary data without touching the booking flows.

v1 caching plan in one paragraph

Don't pre-index prices. Run live + 10-min TTL Redis cache with stale-while-revalidate. Log every result to price_observations from day one. Maintain a route-index and schedule-cache via a nightly job over the top routes. Maintain a negative cache for "no service" results. Defer airline scraping indefinitely. Revisit at ~1k DAU: by then the price-history database is meaningful and the next set of decisions (predictive deal scores, seeded scrapes at scale) can be made with data.

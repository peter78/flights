Ground Transit & Intermodal

The most operationally complex piece of the system. Multiple modes × asymmetric data quality × time-sensitive composition.

Journey shape

A trip is no longer just a flight:

[GroundLeg A → DEP_n]  +  [FlightLeg DEP_n → ARR_m]  +  [GroundLeg ARR_m → B]

For a typical search you might evaluate:

  • 3–8 candidate origin airports × 3–8 candidate arrival airports
  • × 2–4 ground options per side (drive / train / bus / transit)
  • × 5–20 flight options per airport pair

= thousands of composite journeys before ranking. The win is ruthless pruning, not exhaustive search.

Catchment area — which airports are even reachable?

Naïve radius is wrong everywhere (mountains, water, no roads). Two better options:

1. Pre-computed isochrones (recommended for v1)

  • For each airport, pre-compute "ground area reachable within T hours" once a quarter using Mapbox Isochrone / Valhalla / OpenRouteService.
  • Store as polygons in Postgres + PostGIS.
  • Query: "which airports' isochrones contain the user's point?" — millisecond lookup, zero live routing calls.

2. Live routing per candidate

  • Pull all airports within radius_max (e.g. 300km).
  • Live-route to each (1–2s per call). Accurate, expensive.

Hybrid (the actual recommendation)

Isochrone filter to ~5–10 candidates, then live routing for the survivors.

Pruning strategy (so it doesn't explode)

Order matters. Cheapest pruning first:

  1. Isochrone filter → candidate airports (no routing calls).
  2. Negative cache + route index → drop dep/arr pairs with no service (no provider calls).
  3. Rough lower-bound flight cost → from price_observations, prune pairs where even the historical minimum + cheapest ground > current best total.
  4. Live flight queries in parallel, capped at top-K pairs (e.g. K = 10).
  5. Ground routing in parallel for surviving airports.
  6. Composition + ranking.

With this, a typical search is ~10–15 live provider calls instead of thousands.

v1 provider lineup (US + EU, all modes, real prices where API allows)

Driving / car

Mapbox Directions (US + EU, cheap, traffic-aware enough). Wrap behind DrivingProvider.

Local transit (city ↔ airport)

Google Directions Transit mode for both US and EU metros. Best per-city quality without integrating 50 GTFS feeds yourself.

Long-distance rail

  • EU: Deutsche Bahn HAFAS (covers DE + cross-border into FR, AT, CH, NL, BE, IT, DK, PL). Single integration unlocks most of EU.
  • EU national gap-fillers: SNCF open data for FR-internal, Renfe for ES — v1.5.
  • UK: National Rail Enquiries (free) for schedules; Trainline partnership for prices later.
  • US: Skip rail for v1 (Amtrak rarely competitive with flying, no clean API). Revisit.

Long-distance bus

  • FlixBus API (US + EU, since they acquired Greyhound).
  • Wanderu as fallback for US routes FlixBus doesn't cover.

Discovery / fallback

Rome2Rio for "is there any way from X to Y" queries when none of the above return results. Used as a discovery API, not the primary source.

The TransitProvider interface

class TransitProvider(Protocol):
    name: str
    modes: set[Mode]              # {DRIVE, RAIL, BUS, TRANSIT}
    regions: set[Region]          # {US, EU, GLOBAL}
    pricing: PricingLevel         # LIVE | ESTIMATE | NONE
    bookable: bool

    async def route(
        self,
        origin: GeoPoint,
        dest: Airport,
        when: Datetime,
        passengers: int,
        bags: int,
    ) -> list[GroundOption]: ...

@dataclass
class GroundOption:
    mode: Mode
    legs: list[GroundSegment]        # e.g. [walk, train, transfer, train, walk]
    depart: Datetime
    arrive: Datetime
    price: Money | None
    pricing_confidence: Live | Estimate | Range
    arrival_uncertainty_minutes: int
    bookable: bool
    booking_url: str | None

The orchestrator queries providers in pricing priority order — live first, fall back to estimate only if no live provider covers the corridor.

Key operational notes

HAFAS quirks

DB's HAFAS endpoint isn't formally public. The mobile-api variant is more stable for programmatic use. Several OSS wrappers exist (db-vendo-client, hafas-client in JS, python-hafas-client). Use one; don't roll your own protobuf parsing. Be a good citizen with rate limits — DB has tolerated this informally for years but can change.

Mapbox isochrones

Free tier is 100k requests/month. Pre-computing 200 airports × 4 time bands (30/60/90/120 min) × 3 modes = 2,400 requests once a quarter. Comfortably free.

Google Directions pricing

$5/1k requests for Directions, $10/1k traffic-aware. Budget: ~10 calls/search × 1k searches/day = ~$1,500/mo. Significant. Mitigation: cache route shape (postcode → airport) for 24h since driving routes between popular pairs change little — reduces calls 5–10×.

FlixBus

Partner API is approval-gated but generous. While waiting for approval, you can use their public site's underlying JSON endpoints (same legal posture as fast-flights with Google).

Protected-intermodal deep links

Every airline's flow is bespoke. LH lets you select rail+flight together in standard booking; AF TGVAir requires specific landing pages. Document each one and store deep-link templates; revisit when they break.

Risks specific to ground transit

  • HAFAS access changes: if DB tightens, EU rail coverage drops to "estimates only". Mitigation: Rome2Rio fallback; design for graceful degradation (pricing → estimate, not error).
  • Connection-rule wrongness: getting min_check_in wrong by 30 minutes silently over- or under-promises feasibility. Maintain a per-airport overrides table (LHR T5 transfers, JFK terminal hops, etc.).
  • Protected-intermodal staleness: airlines add/drop programs quietly. Quarterly manual review of the rules table.
  • Mapbox isochrone ≠ reality: isochrones don't model time-of-day. Use them only as a candidate filter, never for the displayed ground time — that always comes from live routing.
  • Parking is sneaky: a $400 flight + "free" drive can be a $700 trip with 7 days at airport parking. Always include in the breakdown.
  • Edge: ferry-served airports (parts of Greece/Croatia, Nice region). Rome2Rio handles; self-built does not.

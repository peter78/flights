Roadmap & Risks

A phased build that delivers value early and saves the expensive integrations for after the core engine has shape.

Phase 0 — engine (1–2 weeks)

  • FlightProvider interface + FastFlightsProvider adapter.
  • SearchRequest / Journey / Leg data model.
  • Orchestrator with open-jaw and multi-origin fan-out.
  • Pytest suite with recorded HTML fixtures so tests don't hit Google.
  • price_observations append-only logging from day one.

Phase 1 — NLU & cost (1–2 weeks)

  • Claude Haiku NLU with disambiguation flow and prompt caching.
  • Fee KB schema + initial 20-airline seed (manual or one-shot LLM extraction).
  • Cost-aware ranker with composite scoring.
  • FastAPI endpoints + SSE streaming.
  • NLU eval harness (50 hand-graded queries, CI-gated).

Phase 2 — ground infrastructure (1 week)

  • TransitProvider interface + MapboxDrivingProvider + GoogleTransitProvider.
  • Isochrone pre-computation pipeline (~200 airports, one day of compute).
  • Curated city_groups (top 50) + protected_intermodal rules.
  • Connection-validation logic with min-buffer table.

Phase 3 — rail / bus integration (1–2 weeks)

  • DBHafasProvider (biggest single EU rail coverage unlock).
  • FlixBusProvider (US + EU bus).
  • Rome2RioProvider as discovery fallback.
  • Composition: [Ground, Flight, Ground] journey assembly with connection-rule enforcement.

Phase 3.5 — places & multi-stop planning (1–2 weeks)

  • PlaceProvider interface + OSMPlaceProvider (Nominatim + Overpass + Wikidata) + GooglePlacesProvider adapter.
  • resolve_poi NLU tool with disambiguation flow.
  • Multi-stop trip composition: cluster POIs by city → infer flight legs between clusters → ground transit within.
  • place_cache table with provider-aware TTLs (7d under Google's 30d ToS cap, 30d for OSM/Wikidata).
  • Affiliate-partner registrations (OpenTable, Viator, GetYourGuide, Tiqets) on a parallel, slower clock.
  • See Places & POI for the provider lineup and the three cost models.

Phase 4 — web UI (2–3 weeks)

  • Next.js PWA — doubles as mobile v0.
  • Chat input with disambiguation prompts inline.
  • Itinerary cards with cost breakdown table, "Protected" badge, deep-link out.
  • Result streaming via SSE (cheapest-so-far while fan-out continues).

Phase 5 — caching layer (1 week)

  • Redis search-result cache with stale-while-revalidate.
  • Negative cache for "no service" results.
  • Route index + nightly schedule cache for top routes.

Phase 6 — protected intermodal & risk modeling (2 weeks)

  • Protected intermodal detection in journey composition.
  • Deep-link generation to LH Express Rail / AF TGVAir / KLM&NS / BA Rail&Fly bookable flows.
  • Initial missed-connection risk score (heuristic for v1, statistical later).

Phase 7 — mobile + booking (when justified)

  • If PWA traction warrants: React Native / Expo wrapper.
  • If booking enters scope: swap one airline to Duffel as a proof; keep fast-flights as fallback discovery.
  • Affiliate partnerships (Trainline, FlixBus, Omio) for bookable ground legs with revenue share.

Total timeline

Phases 0–6 are roughly 10–15 weeks for one engineer working full-time, depending on how clean the HAFAS integration goes and how much UI polish is taken on in Phase 4. Phases 0–1 (~3 weeks) deliver a working text-in, ranked-results-out engine; Phases 2–3 (~3 weeks) add the multimodal magic; Phase 3.5 (~1–2 weeks) adds multi-stop trip planning; Phase 4 (~3 weeks) ships a usable product.

Risks worth tracking

External / vendor

  • Google blocking fast-flights at scale. Mitigation: Bright Data already wired, budget for residential proxies. Plan B: Kiwi Tequila free tier for discovery, swap providers without orchestrator changes.
  • HAFAS access changes. Mitigation: TransitProvider abstraction degrades gracefully to Rome2Rio estimates. Flag pricing confidence to user.
  • Rome2Rio commercial terms shift. Mitigation: self-built EU coverage (HAFAS + Mapbox + FlixBus) covers the high-value corridors without Rome2Rio.
  • Anthropic pricing / availability. Mitigation: LLMProvider abstraction, eval harness, configured fallback.

Data quality

  • Fare-brand assumption wrongness. v1 totals are estimates because fast-flights doesn't return brand; basic-economy assumption can over- or under-state by $30–80/leg. Be loud about this in the UI.
  • Fee KB staleness. Mitigation: weekly refresh, diff-flagged review.
  • Connection-rule wrongness. Mitigation: per-airport overrides for the worst offenders; user feedback loop.
  • Protected intermodal program changes. Mitigation: quarterly review of the rules table.

Operational

  • Fan-out latency. Mitigation: SearchBudget caps, SSE streaming so users see progress, isochrone + route-index pruning.
  • Cost explosion if popular. Mitigation: Redis SWR cache cuts provider calls 70–90% on popular routes; cache route shapes 24h for driving directions.
  • Parser regressions. Mitigation: schema sentinels in the fast-flights parser; daily canary; staged version upgrades.

Legal / commercial

  • fast-flights vs Google ToS. Grey area at low volume; problematic at commercial scale. Migrate to legitimate providers before monetizing aggressively.
  • Direct airline scraping risk. Avoid entirely; only scrape published fees pages (different posture than booking flows).
  • Booking liability. Stay deep-link-out for v1. Don't take payments. Booking changes legal posture significantly.

Open questions to revisit

  • Do we want a public API once the engine exists? (Affects how strict the request/response schemas need to be.)
  • Loyalty programs — bag waivers, status perks — are these v2 or never?
  • Trip planning beyond search: saved searches, price-drop alerts, share-with-companion? Each is a real feature, none are blocking the core.
  • Long-term LLM mix: at what traffic does OSS NLU pay back the eval engineering?
  • Affiliate booking revenue: which integrations to prioritize for revenue share?

Definition of v1 done

v1 ships when A user can type a natural-language query for a complex trip (open-jaw, multi-airport, intermodal, date-flexible), see ranked journey options within a few seconds, with each option showing a total-cost breakdown including bags and ground transit, and click through to bookable destinations (airline / rail operator / FlixBus) directly.
